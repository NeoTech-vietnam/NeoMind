# VS Code model bridge

NeoMind keeps this signed local-host Bridge as an optional strict execution path. Full Copilot-native workflows use standard visible VS Code subagents without enabling it. All active extension, command, configuration and protocol IDs now use NeoMind; historical signed receipts remain readable without rewriting their bytes; see [Copilot runtime](copilot-runtime.md).

Automated `manager_run`, CLI `workflow run`, and `native_dispatch` can use existing VS Code language-model providers. This path runs inside a desktop/remote VS Code extension host, not Copilot CLI, the Copilot SDK, or Codex App Server. No authenticated model requests are made during installation or tests.

## Upgrade from the previous namespace

Disable and remove the old TaskForces or VeryThinker Bridge extension before installing this NeoMind identity. Set the new User setting `neomind.bridge.runtimePath` to a trusted `neomind` runtime, then explicitly enable it. Active host sessions do not migrate across protocol IDs; review interrupted state and start a fresh bounded invocation. The old runtime package is not accepted by the new extension.

Run `npx neomind migrate` to atomically move an existing `.taskforces` or `.verythinker` directory to `.neomind`, then `npx neomind update` to refresh managed integrations. Migration never rewrites signed receipts or historical record bytes. Edited obsolete generated files remain preserved with warnings for manual resolution. Saved project repository/archive destinations are preserved. New automation uses the NeoMind package repository.

## Install and enable (Windows)

1. Build this checkout with `npm run build` in `D:\workspace\NeoMind` (install its existing dependencies first if absent). Alternatively install a tarball containing `dist`, dependencies, and `extensions/vscode-model-bridge` in your project.
2. Install the supplied package with `code --install-extension D:\workspace\NeoMind\artifacts\neomind-agent-monitor-0.1.0.vsix`, or select that file through VS Code's **Extensions: Install from VSIX** command. For development without installation, launch `code --new-window --extensionDevelopmentPath=D:\workspace\NeoMind\extensions\vscode-model-bridge D:\path\to\initialized-project`. A manual source installation can instead copy the complete `extensions/vscode-model-bridge` folder, including `monitor.cjs` and `resources/`, into `%USERPROFILE%\.vscode\extensions\neomind.neomind-model-bridge-0.1.0` while VS Code is closed. Use the source folder under your installed runtime package when applicable. The extension has no npm dependencies or build step; `code --install-extension` accepts a VSIX or extension ID, not a source folder.
3. Open VS Code **User Settings (JSON)** and set `"neomind.bridge.runtimePath": "D:\\workspace\\NeoMind"`. For a tarball install, use the absolute package directory, for example `D:\\project\\node_modules\\neomind`. This is executable trusted code; workspace overrides are deliberately ignored. Node must meet the package's engines requirement for CLI/MCP. The extension host must support the stable VS Code LM tool API (VS Code 1.109+).
4. Open the initialized project as an exact workspace folder and enable Workspace Trust only after reviewing it. Register and authenticate the intended model providers in VS Code as usual. In `.neomind/routing.json`, retain your selected `strong_provider`, `strong_model`, `worker_provider`, and ordered `worker_models`. Add `"vscode_effort_policy": "allow-unavailable"` only after accepting the compatibility ceiling below. Omission or `"require-verified"` blocks execution because the stable API cannot verify reasoning effort.
5. Run **NeoMind: Enable Model Bridge** from the Command Palette in that workspace. Select the exact folder if using multiple folders and explicitly approve the modal prompt. Nothing starts automatically on extension activation. Accept VS Code's separate model-access consent when requested; refusal blocks the invocation.
6. Submit your ordinary requirement through the existing NeoMind MCP `manager_run`, or run `npx neomind workflow run --requirement "Inspect and implement my bounded requirement"` in the initialized project. Keep VS Code and the owning CLI/MCP process alive. CLI observation/lifecycle syntax remains available through `npx neomind --help`. No extra daemon or headless authentication is needed.
7. Run **NeoMind: Disable Model Bridge** to revoke access. Closing/reloading the extension host or changing workspace folders also requires explicit re-enablement. Active invocations become interrupted/blocked, never successful because the host vanished.

The CLI and bridge must run on the same machine, OS user, filesystem, and workspace root. For SSH/containers/WSL, enable the workspace extension on the same remote side as the CLI. Distinct symlink aliases resolve to the same real root; a parent, child, different folder, or copied project cannot reuse the descriptor.

For the monitor alone, complete installation, the User runtime setting and workspace selection, then run **NeoMind: Open Agent Map**. Its animations replay recorded relationships and distinguish signed receipts from reported native records. Steps 5–7 enable optional signed inference and are unnecessary for viewing saved activity.

## Model policy and truthful receipts

- The host calls `vscode.lm.selectChatModels({ vendor, id })` and invokes the single returned object's `sendRequest`. Both observed `vendor` and `id` must match; no request-provided model/provider claims establish success. A display-name provider in `routing.json` resolves through `language_models_file` to exactly one catalog vendor. Model IDs remain exact IDs, not display names. A manually configured bridge policy without a catalog uses provider fields as vendor IDs (default `copilot`); the monitor/model-control setter requires a configured catalog for custom providers. Ambiguity blocks; do not guess between providers sharing a vendor and ID.
- Workers try the next configured ID only when exact selection returned no models. Authentication/consent refusal, quota, request errors, unsupported tools, or failed inference never trigger fallback. Strategic roles never fall back.
- Production receipts use issuer `neomind-vscode-lm`, execution mode `vscode-extension-host`, and `identity_provenance: local-vscode-extension-host`. Conversation and turn IDs start with `vscode-host:conversation:` / `vscode-host:turn:`. These IDs are host-issued, **not provider session IDs**. The host reports VS Code's version. Codex version/integrity/sandbox checks remain separate and unchanged for Codex/fixture receipts.
- This is signed **local extension-host attestation** of the selected VS Code API object and completed response/tool loop. It is not provider-issued cryptographic proof of an endpoint, backend model, token usage, or provider honesty. A malicious local user/extension with access to the same account or signing key is outside this boundary. Never describe these receipts as stronger provider attestation.
- The stable API does not verify reasoning-effort controls. `confirmed_reasoning_effort` stays `null`, `effort_support` is `unavailable`, and requested policy remains recorded. `allow-unavailable` explicitly permits that ceiling; it does not acknowledge high/low effort. No undocumented `modelOptions` are sent. Use `require-verified` (or omit the field) when verified effort is mandatory.
- No builtin shell or filesystem tools are provided, for **any** role. `native_sandbox` stays `null`: absence of shell is not an OS sandbox. Only role-scoped invocation-bound NeoMind MCP tools enter the tool list. First request requires a real tool-call round before successful completion; stable model objects need not expose capability metadata. Unsupported/ignored tool calling blocks.

## Gateway, lifecycle and security

The model loop runs in the extension host. MCP dispatch remains in the owning CLI/MCP process using the existing MCP SDK's linked in-memory transport and `createMcpServer` bound to the invocation ID. This deliberately avoids spawning a second CLI owner: manager tool calls can dispatch/wait/interrupt/resume workers without losing their native session ownership. No alternate MCP protocol implementation or extra dependency is used.

Manager's signed running receipt and workflow binding are persisted **before** model requests or tool execution. Each tool call reuses existing role, workflow, task, write, independent-review, configuration, and active-invocation checks. Recursive `manager_run`/`manager_begin` are not offered and are denied by MCP; manager dispatch of another manager is denied too. Worker requests run concurrently while the manager polls or waits. Tools can still run reviewed prescribed checks, perform scoped source writes, use approved providers, or publish through existing gateway policy; no-shell does not make those operations harmless. Strategic roles have no general shell tool.

The host listens only on `127.0.0.1` with an ephemeral port and fresh 256-bit token and instance ID. Descriptor lives in a user-private OS temp directory, not the project. Unix modes are 0700/0600; Windows removes inherited directory access and grants the current user access via `icacls.exe`, failing closed if that fails. Token never enters receipts, stdout, generated files, or Git. HTTP requests require token and instance ID, reject browser Origin, never follow redirects, and do not echo request/provider secrets in errors. Loopback access alone is not authentication. Protect your OS account and installed extensions; same-user malicious code is not isolated.

Limits: 1 MiB request/response payloads, 64 concurrent connections, 15-second HTTP limits, 10-second model selection, 64,000 output characters, 32 tool calls per response, 128 rounds, 256 host turns/conversations per enablement, bounded context, 75-second MCP requests, 30-minute invocation deadline, and 90-second owner heartbeat. Cancellation reaches the VS Code cancellation token and pending MCP requests. Disabling closes connections and clears host conversations. Cancellation cannot roll back a tool mutation already committed; resume must reinspect durable state and hashes. Stalled/noncompliant provider extensions cannot be forcibly killed without ending their extension host, but receive cancellation and can no longer deliver gateway operations.

Routing, project/native/tool configuration and optional catalog content are hashed at start and checked during tool execution/completion. Provider/model/catalog changes invalidate current acceptance and resumption. Catalog credentials are hashed, never copied. Stale descriptor, missing host, lost trust, ambiguous selection, consent refusal, unsupported tools, cancellation, and configuration changes become signed blockers.

Within the same live host, resume creates a fresh signed invocation and host turn while reusing bounded in-memory conversation history. Canceled incomplete tool rounds are removed; durable MCP state remains authoritative. After host restart/history loss, resume blocks instead of fabricating provider history. Start a fresh bounded invocation after reviewing saved workflow/task state; automatic cross-host conversation reconstruction is not implemented. Existing project histories and completed receipts persist normally. CLI owner loss ends the gateway; heartbeat cancels the model. Receipts remain active until existing orphan reconciliation marks the absent owner; they cannot authorize tools without a live owner.

## Known execution limits

- Existing prescribed checks and some provider setup operations use synchronous subprocesses in the CLI owner. They can stall all invocation polling. A tool exceeding the 75-second MCP deadline or blocking owner heartbeats for 90 seconds can block the workflow, even when its subprocess eventually succeeds. Long-running automated checks need asynchronous, cancellable gateway execution; this bridge does not yet provide that. Reinspect durable results before retrying: cancellation does not undo side effects.
- With an ended VS Code coordinator and changed routing/configuration hashes, `manager_run` starts a fresh coordinator inside the same saved workflow. Unchanged configuration attempts to resume bounded in-memory history; after host restart that history may be unavailable and resumption can still block. Inspect the saved blocker and workflow before starting fresh bounded work. Historical receipts remain intact.

## Validation

`test/vscode-extension.test.mjs` covers explicit enablement, User-only runtime settings, and revocation during folder selection, consent, import, and host startup. Late startup closes its host instead of re-enabling access.

`test/vscode-host.test.mjs` uses deterministic fake VS Code model/message/cancellation APIs with the real authenticated loopback server, signed native receipts, real MCP SDK transport, and existing scoped gateway. It exercises manager mutation/worker dispatch/wait, truthful model/provenance, policy checks, refusal, unavailable models/tools, interruption/resume, shutdown, and tampering. Fake tests make no network inference and establish no real account/model availability. Live VS Code/provider smoke testing requires explicit human enablement and consent; it is not implied by passing repository tests.
