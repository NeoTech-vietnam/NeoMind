# Agent map research for NeoMind

Inspected on **2026-10-23** using upstream repositories and first-party product documentation. No upstream instructions were executed. This note supports the implementation choice; it does not establish live provider behavior or definitive provenance of the user's screenshot.

## Findings and attribution

**Nimbalyst is useful orchestration inspiration, but the attached farm screenshot has not been identified as a Nimbalyst feature.** Its primary README describes parallel agent sessions, optional worktrees, session kanban, heterogeneous providers, and links between sessions and edited files. The extension architecture provides a host contract around visual editors. Its current tree also contains a disabled-by-default Crew alpha extension for persistent scheduled members. None of the inspected material establishes that the supplied Vietnamese pixel farm belongs to Nimbalyst. [Pinned README](https://github.com/nimbalyst/nimbalyst/blob/aa40e515a2841d4439f9ea15d2f9dc5387e0478e/README.md), [extension architecture](https://github.com/nimbalyst/nimbalyst/blob/aa40e515a2841d4439f9ea15d2f9dc5387e0478e/docs/EXTENSION_ARCHITECTURE.md), [Crew manifest](https://github.com/nimbalyst/nimbalyst/blob/aa40e515a2841d4439f9ea15d2f9dc5387e0478e/packages/extensions/crew/manifest.json).

Nimbalyst's agent-provider architecture document is explicitly a **draft**, dated April 25, 2026; it should not independently prove shipped support. Its implemented provider registry is a stronger code reference for separation between the application shell and provider adapters. Adopt that boundary without importing its Electron application into the NeoMind VS Code extension. [Draft design](https://github.com/nimbalyst/nimbalyst/blob/aa40e515a2841d4439f9ea15d2f9dc5387e0478e/design/agents/agent-provider-architecture.md), [registry source](https://github.com/nimbalyst/nimbalyst/blob/aa40e515a2841d4439f9ea15d2f9dc5387e0478e/packages/electron/src/main/extensions/AgentProviderRegistry.ts).

**Pixel Agents** is a closer functional match to animated agents in VS Code. It represents terminal agents as characters, reflects actual activities, displays permission/input bubbles, and distinguishes subagents and teammates. Its current README separates implemented Claude Code integration from future provider expansion, so it does not establish universal Codex/Gemini compatibility. Its typed hook-provider boundary is a useful pattern for adapting execution telemetry. [Pinned README](https://github.com/pixel-agents-hq/pixel-agents/blob/b1bafd02896d90d83457266575a1e8e5011ce997/README.md). The original `pablodelucca/pixel-agents` URL currently resolves to this project.

**AI Monitor** is another close visual reference: its first-party README describes a local bilingual monitor, a VS Code extension, activity-driven office characters and smaller subagent helpers. Its source includes a procedural farm scene and messages about intersession `SendMessage` names. The exact four quadrant labels, oracle character and interaction wording from the attachment were not matched in this inspected revision, so this is a similar implementation rather than a confirmed screenshot attribution. [Pinned README](https://github.com/hominhtuong/AIMonitor/blob/605399b7a6403c17bc33f237bd19a0f424c147d0/README.md), [farm scene](https://github.com/hominhtuong/AIMonitor/blob/605399b7a6403c17bc33f237bd19a0f424c147d0/aimon/static/scene-farm.js), [office and subagent rendering](https://github.com/hominhtuong/AIMonitor/blob/605399b7a6403c17bc33f237bd19a0f424c147d0/aimon/static/office.js), [localized messaging descriptions](https://github.com/hominhtuong/AIMonitor/blob/605399b7a6403c17bc33f237bd19a0f424c147d0/aimon/static/i18n.js).

**Agent Town** supplies a small framework-independent Canvas visualization, procedural characters, multiple scenes including Farm & Ranch, status changes and click callbacks. It is a potential replaceable renderer, not evidence of a compatible NeoMind orchestration protocol. Its playground dashboard includes simulations; displayed demo conversations should not become engineering evidence. ## Recommended contract and implementation

Expose a read-only `readAgentMap(root)` projection that both CLI and VS Code can consume. Agent identities must come from verified local invocation receipts, with the execution mode displayed. Workflow/task nodes can come from ordinary engineering records and must be labeled accordingly. For unsigned native execution, task/workflow records remain visible without manufacturing a signed agent identity.

Each node needs a stable source ID, role, lifecycle state, update time, and optional observed/requested model metadata. Each edge needs explicit endpoints, relationship kind, evidence ID, source type and timestamp. An invocation's workflow membership is not proof that it exchanged a message with every other participant. The current receipt schema records resume ancestry (`prior_invocation_id`), workflow and task bindings; it does not establish an independent parent/spawn telemetry stream. Render only those relations and actual contribution/report records. Label animated dots as replay of recorded relations rather than live chat. Add a dedicated signed dispatch/message event only when runtime support can produce it.

Keep the renderer independent from the orchestrator. The VS Code extension reads bounded projections, honors reduced motion, escapes all displayed text, and routes model changes through the core's policy helper. Models apply to the next invocation; live invocations retain their recorded configuration. API keys, prompts, raw output, permission payloads and provider credentials never enter the map snapshot.
