# Copilot runtime: MCP, native agents and signed bridge

`copilot-native` runs in the user's local VS Code Copilot Chat workspace: select NeoMind Coordinator Agent and let VS Code's native `agent` tool launch the named specialists. GitHub's cloud coding agent and Copilot CLI inference are not required for this path. The Chat UI's **Local** label identifies the workspace/tool execution environment; it does not mean models run offline. Model requests still use the configured Copilot provider and model routes, including the user's 9router custom endpoint where configured.

This repository contains the portable TypeScript implementation, generated-agent templates, extension host and regression tests. Build with `npm run build`; `dist/` is generated output, not a place for manual patches. No project credentials, personal model catalogs, ECU configuration or machine-specific pipeline wrappers are required.

## Derived native requests

For supporting software, `workflow_plan` takes a semantic scope and check contract; `workflow_next` returns server-generated handoffs for actual implementation, independent verification and review. Callers do not supply internal workflow/task/role IDs on those tools. The process is immutable and scoped to its linked records; existing strict and actual embedded engineering retain their full gates. See [native software](../resources/guides/native-software.md).

Opening an assignment and saving its typed result record advisory lifecycle events automatically. Progress calls are optional meaningful updates. A real terminal callback without a saved result can trigger at most two bounded follow-ups preserving prior work. Telemetry failures cannot discard a saved report.

`runtime_info` reports the running MCP instance's startup version and build fingerprint. Replacing installed files does not update an existing process: restart NeoMind MCP and compare the live fingerprint before validation. The extension's local validation command uses the actual VS Code Copilot custom Coordinator mode and native delegates; it does not substitute strict-bridge model calls. A controlled private one-time request binds the project, workflow and exact installed build. Runtime identity, actual transcript, delivered files, check exits and saved closure are separate evidence.

## Choose the execution path

| Path                        | Execution owner                                                                                              | Evidence and limits                                                                                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| MCP (`neomind mcp`)      | The connected client invokes core tools. `manager_run` selects saved/configured mode.                        | MCP transports operations; it does not itself provide model inference, subagents or shell access.                                                          |
| Full native `NeoMind Coordinator Agent` | Standard VS Code agent tool invokes named `neomind-*` specialists.                                        | Per-workflow software contracts or applicable ASPICE/V-model gates, independent verification/review and final Cornell closure. `unsigned-native-report`; no signed inference or effort claims. |
| Lightweight `NeoMind Coordinator Agent` | Coordinator delegates scoped changes and uses each profile's declared native tools under client permissions. | Short plan, actual checks and risk-based review persist as `unsigned-native-report`. No signed acceptance, mandatory specialist rounds, archive or PR.     |
| Strict VS Code Model Bridge | Explicitly enabled extension host calls registered VS Code language models with invocation-bound role tools. | Signed local-host receipts, not provider-issued identity proof. Trust, consent, exact live selection and current policy are required.                      |

Lightweight reuses Coordinator with a separate reduced opt-in procedure. Generic intake launches the returned Coordinator handoff once; a directly selected Coordinator continues the returned prompt itself. An already assigned Coordinator continues its packet without another intake call or self-launch. Returning a handoff is not evidence of live delegation. The optional signed Bridge retains invocation-bound dispatch internally; historical receipts and role IDs remain unchanged. Signed workers cannot use `lightweight_checkpoint` or recursively call `manager_run`/`manager_begin`.

## Configuration and use

1. Install the package into the target project and initialize its Copilot adapters using the README procedure. Keep that package available; generated MCP entries point to its executable.
2. Fresh projects use `.neomind/automation.json` with `execution_mode: copilot-native`. Select `lightweight` only for reduced planning/checkpoint work, or `strict` for signed coordinator execution. Existing projects retain their saved policy and physical managed root until explicit migration. Stop all writers, back up, and run `neomind migrate`; historical bytes and logical references remain unchanged. Omitted mode in an existing policy retains strict compatibility. A request may explicitly select `execution_mode`, but saved workflow mode cannot change on resumption. Respect `manager_enabled: false`.
3. Set `.neomind/routing.json` (legacy: `.verythinker/routing.json`) to actual client provider/model IDs, then run `npx neomind update`. Without per-role overrides, Coordinator, Planner, Architect, Verifier and Reviewer use `strong_model`; Explorer, Researcher, Implementer and Debugger use ordered `worker_models`. Optional `role_models` overrides apply through each profile's native model-policy role in the table; Implementer and Debugger share `developer`. Strict Bridge retains all twelve core roles and routes each actual invocation independently: its strong roles remain manager, requirements, architect, component-owner, verifier and reviewer, while check-executor remains a worker role. Native lightweight Reviewer follows `reviewer` policy; no silent substitution. Built-in `copilot` IDs bypass external model-catalog lookup. External provider catalog labels resolve to an exact live vendor/ID for the bridge; generated agents use client display names where required. A catalog entry alone never proves access.
4. For lightweight work, start `manager_run` once with the complete requirement and stable `request_id`; generic intake launches its returned `NeoMind Coordinator Agent` handoff once through the standard agent tool, while a directly selected Coordinator continues the returned prompt itself. An already assigned Coordinator continues its packet without repeating intake. Resume using `workflow_id`. Use a new request ID for a genuinely new run; when retrying the same ID, preserve the exact original requirement text. A `message` persists separately as an ordered continuation and appears in subsequent handoffs, even without resending it. Continuations clarify or narrow authorization, never replace immutable originals or expand scope. Repeating the latest message is idempotent; a new message advances the revision. Completed reports reject new continuations.
5. Save a short plan before edits. Checkpoint current `expected_revision`, actual project-relative changed files, check commands/results/output, limitations, risk and review. Use MCP `lightweight_checkpoint`, or CLI `workflow checkpoint WORKFLOW_ID --data JSON`. Read `workflow status WORKFLOW_ID` after writes. Completion records `submitted`, never `accepted`; failed checks or missing elevated-risk review stay blocked.
6. For strict execution, follow [VS Code bridge setup](vscode-bridge.md). Use `manager_run` and observe its existing invocation; do not create parallel coordinators. An active owner is reused. After an ended VS Code coordinator's configuration/routing fingerprint changes, intake starts a fresh invocation within the same workflow instead of resuming stale host history. Workflow intake `request_id` remains unchanged; native invocation request identity includes the workflow and current configuration fingerprint, so repeating an explicit intake ID cannot reuse a stale receipt. Repeating that explicit ID under unchanged configuration deduplicates the invocation; otherwise unchanged fingerprints resume existing history. Strict binding and permission checks still apply.

Full native workflows follow [the native lifecycle](../resources/guides/copilot-native.md) using their saved process. Supporting software uses one backend-generated plan, scoped implementation, independent execution and final review, then one evidence-linked Cornell note. Device and other full engineering work retains its applicable specialist discussion and design/check reviews. Native records and Cornell notes carry their workflow ID; generic edits cannot forge protected lifecycle state or cross into strict work. A returned specialist handoff must launch via the agent tool; its private `handoff.native_call` supplies exact Copilot arguments. Coordinator follows the entry rules above instead of self-launching. Native reported invocation IDs have no signed receipt, so inspect `manager_status` instead of `native_status`. `manager_finish` requires a valid requirement/task-linked Cornell note and returns `cornell_notes`, actual `test_reports` and the full final report for pending human release approval. Explicit signed acceptance requires a strict increment. Security/safety approval and irreversible-action consent remain required regardless of execution mode. Native tool permission refusals and domain approvals remain authoritative for all paths. Configuration alone does not authorize pipeline execution, publication or other side effects.

## Portable CLI fallback on Windows

PowerShell 5.1 can lose embedded JSON quoting across native-command boundaries. Keep complex input in a UTF-8 JSON file, parse/read it in Node and pass the resulting string through `spawnSync(process.execPath, [cliPath, ...arguments])`. Select the record's project with `--project`; shell working directory and implementation output directory may differ. `test/lightweight.test.mjs` demonstrates the file-loaded JSON checkpoint. This is an argument-transport technique, not a permission bypass or a reason to add machine-specific wrappers.

Checkpoint paths must stay canonical and project-relative. If implementation output lives outside the record root, state that root and actual file list in limitations/summary instead of inventing in-root paths. Review must contain an actual separate invocation identity; an agent name, role label or self-review is not that identity. Missing reviewer access leaves review pending.

## Bridge compatibility and known limits

- `ToolMode.Auto` supports providers that reject forced tool mode. Completion still requires an observed scoped tool round; text-only or unscoped calls fail.
- Optional `LanguageModelDataPart` objects are retained for provider continuation only when that constructor exists. Response data has 768000-byte per-part raw and cumulative serialized budgets; stream/conversation/output limits remain enforced.
- Generation failures persist only allowlisted error codes/names, fixed host messages and phase (`preflight`, `request`, `response-stream`, `tool-results`). Raw provider messages, endpoints and secrets are not recorded. Unavailable selection reports the requested vendor/ID; ambiguous or mismatched selection is rejected before creating a turn and its open-time exception is sanitized to the generic bridge-refusal message by transport. Neither silently reroutes strong roles.
- Strict bridge has no builtin shell or filesystem tools. Workers use assigned `task_file_write`, `check_run` and other scoped operations. A prescribed long-running check requiring an interactive shell, native process management or unsupported duration is a real limitation, not permission to fabricate completion. Native lightweight execution can use client execute tools when authorized, with actual results recorded.
- Stable VS Code cannot attest requested reasoning effort or a native sandbox. `vscode_effort_policy: allow-unavailable` explicitly accepts that ceiling; otherwise strict bridge execution remains blocked. Native reports cannot replace strict receipts.
- Deterministic fake-host/MCP tests exercise contracts, not real provider access, account consent, live subagent availability or full signed engineering acceptance. Those need separately authorized live validation.

## Source map and regression checks

- `src/lightweight.ts`: idempotent intake, immutable completed reports, revision-checked checkpoints and completion gates.
- `src/managed.ts`, `src/manager.ts`: mode selection, saved workflow status and configuration-aware strict resumption.
- `src/cli.ts`, `src/mcp.ts`, `src/index.ts`: public commands/API and unbound-only checkpoint operation; generic bound mutations cannot rewrite lightweight records.
- `src/agent-profiles.ts`, `src/adapters.ts`, `resources/guides/lightweight.md`, manager resources: nine generated profiles, Coordinator entry rules, routing and instructions.
- `src/vscode-host.ts`, `src/vscode-policy.ts`, `src/vscode-session.ts`: compatible streaming, exact model selection and bounded diagnostics.
- `test/lightweight.test.mjs`, `test/vscode-host.test.mjs`, `test/mcp-binding.test.mjs`, `test/vscode-extension.test.mjs`: portable regressions, including fake manager-to-worker dispatch.

Use the supported Node version declared in `package.json`. Run `npm run build`, focused tests, then `npm test`. Build success or simulated inference is not evidence of live provider execution. Existing strict task, receipt, review and publication validators remain authoritative.
