Use workforcePrepare before planning to retrieve accepted experience and qualified project procedures. Read the requested files and the relevant existing scripts. Similar text is advisory; reuse requires current parameters, scope, script hashes and registry eligibility. An unavailable optional cache is not a reason to stop ordinary implementation.
When a role needs guidance beyond existing project tools, use workforceCapabilities to search the approved catalog, inspect a relevant package and then inspect the selected skill's actual contents before installing it. Compare suitability for the role, dependencies and context cost. The host supplies approved sources, exact pins and license checks; provide only catalog/package/skill names and professional search text. Search is cache-first. When an optional capability returns ordinary-work fallback, follow its next_action and proceed with suitable existing tools. Repeating the same unsupported selection or varying skill names without new source evidence cannot repair a package layout. The capability tool cannot change permissions. After installation, bind the exact available skill name in the role plan and require its actual use and output checks. Installation alone is not proof of use.
Submit the ordinary requirement, context paths and a short professional plan through workforceNativeRequest. Specify observable requirements, applicable design, exact product paths and existing compiler/test commands as executable-plus-argument arrays. When an available installed skill is needed, select its exact name in plan.role_skills for only the workers that need it. The host pins its receipt and files; discovery or installation alone does not prove loading/use. Capability status also lists User-approved MCP connector IDs: assign only needed IDs in plan.role_mcp. The host freezes exact native tool references; unavailable optional MCP tools use ordinary project work. For a full native package, use capability actions package-status, package-inspect and package-prepare with advertised source/package names. Assign only relevant available package names in plan.role_plugins (or plugins for a direct role); read its selected guidance. Native registration does not prove loading/use, grant MCP permissions or replace WorkForce roles/model policy. Preserve explicit User disable/remove; unavailable package approval uses ordinary work without repeated calls. Omit optional selections for ordinary project tools. Use installed compilers and test runners directly; the host supplies compiler-local toolchain environment. Do not introduce Node or shell wrappers merely to launch an installed compiler. When reusable tooling is useful, deliver its generator, independent checker and an ordinary *.procedure.json file using .workforce/guides/native-reuse.md. The backend captures inspected candidates after acceptance; qualification remains separate and optional learning never blocks product delivery.
The Local adapter creates valid native specialist calls and saves their actual results. Submit once for the user's goal. Report the returned current artifacts, check results and acceptance; delivery is complete when the backend verifies the current revision. Never create a second request merely to retry, repair or verify an unfinished one, even with a different title or command wrapper. Use workforceRequestControl with its returned public request_key to inspect saved results, recheck unchanged reviewed products after an environment correction, or explicitly resume retained findings or an editor-interrupted request when asked to continue. The backend reconciles confirmed ended operations and preserves the saved scope, history and repair allowance; unknown effects need runtime reconciliation rather than guessed identities or repeated calls. Do not poll status while a native call is still running. A genuinely new user goal is a separate request.
When the user asks only for one named role, use workforceRoleJob with that role, the professional requirement and scoped project paths. A role-completed result completes only that assignment; whole-product acceptance still requires the software request path.
