# Capture and reuse procedures

For a new repeatable request, call `work_prepare` with the original text, known task family, typed parameters, required outputs, actual client/environment and authorized output scope. Its result is advisory: read the compact brief and account for semantic differences the parameters do not express. Saved full/strict workflows keep their existing lifecycle.

1. Discover before creating: `procedure_discover` finds Node scripts and package commands without executing them. Inspect applicable scripts and the existing recipe catalog. Completion: identify a suitable existing tool or explain what automation is missing.
2. Create only missing automation through the assigned native editor. Generalize repeatable steps into one parameterized Node `.mjs`/`.cjs` script and an independent check script. Reuse the current Cornell compiler/export for note formatting. Completion: actual source files and independently defined expected outcomes exist.
3. Register the actual files with `procedure_register`. Supply the versioned contract, input types, declared dependencies, output paths, environment, write roots, network/publication effects and bounded execution limits. Registration hashes the source and creates a candidate; it executes nothing. Do not invent a successful run or qualify a shipped recipe because it exists.
4. A separate Reviewer inspects the contract and negative-case evidence, then calls `procedure_review` with its own claimed identity. Execution is an unsigned local process; review identity is a declared local attribution, not native attestation.
5. Execute scoped pilots through `procedure_run` in a current in-progress Developer task after current design/check reviews. The runner supplies input JSON on stdin, validates parameters, runs the frozen script and check, and records output hashes. The runner does not submit, accept, close or downgrade an engineering workflow. Continue its actual check/evidence/review operations.
6. Coordinator calls `procedure_qualify`. Eligibility requires a current independent passing review and at least three successful local-process runs across two parameter sets, with current outputs/evidence. Fixture runs do not qualify. A mismatch, failed check or uncertain interrupted run prevents automatic reuse.
7. For later compatible work, use the returned procedure ID/version and fresh parameters. Automatic execution requires eligibility and explicit authorized effects; obtain fresh results/checks. Replaying the same request returns its recorded outcome after integrity checks and does not claim a new execution. New intent requires a fresh request ID.

At completion save the automation disposition in the assignment result lessons: reused an existing procedure, registered a concrete candidate ID/version, or why only shared scaffolding/reporting can be automated. Preserve the original successful and failed work records. This instruction automates the decision to capture tools; script content is produced by the actual assigned worker, not generated from retrieved prose by the database.

The local operator CLI additionally supports `neomind procedure discover|list|show|register|review|run|qualify|suspend|index` and `neomind work prepare|run --data-file FILE`. `work run` is explicit mechanical execution; it never changes an existing engineering workflow. The Automation Library shows statuses and allows candidate registration and suspension. Stored files under `.neomind/procedures` are authoritative; `.neomind/cache/procedures.sqlite` is rebuildable search state. Use `procedure index` to explicitly repair a corrupt search cache.

Local trusted scripts execute with the operating-system user's access. Declared effects constrain dispatch and are not a filesystem or network sandbox. Keep scripts inside the project, declare imported dependencies, pin external packages/tool versions and preserve actual native-client permissions. Initial execution supports Node scripts on Windows/Linux/macOS; non-Node tools can be wrapped by a reviewed Node script.
