# TaskForces: full Copilot-native lifecycle

Use `copilot-native` for visible VS Code subagents with full engineering gates. Read project automation, routing and archive policies before intake. New native policies use `network_policy: local-only` and `automatic_pr: false`; existing saved policies are preserved, and absent `network_policy` retains legacy remote behavior. Under `local-only`, make zero remote discovery, publication or archive requests; explicit remote tools reject. Required workspace research and Cornell findings stay inside the project. Remote work is deferred, not an engineering waiver. New installations use `.taskforces`; unmigrated projects retain `.verythinker`. Serialized historical paths and receipt identities remain unchanged.

## Entry role: decide before intake

- **Generic intake** (not selected Manager and not an assigned specialist): call `manager_run` once with the complete request. Launch exactly `Manager Agent` through VS Code's standard agent tool with the returned `handoff.prompt` unchanged, and wait for its result. A returned handoff is not execution. If launch fails, report the blocker instead of running manager steps inline.
- **Directly selected Manager Agent:** call `manager_run` once for a new user request, then continue the returned prompt and workflow directly in the current invocation. The returned `handoff.agent: Manager Agent` names yourself; do not launch it. An already assigned Manager with a supplied workflow/prompt continues directly without another intake call or self-delegation.
- **Assigned specialists:** execute only the bounded assignment and role contract. Requirement text in the packet does not authorize intake. Never call `manager_run`, launch Manager or delegate recursively. Return actual results, invocation ID and `assignment_report` ID to Manager, not workflow closure.

Resume saved workflow IDs instead of duplicating work. For an existing increment, inspect `manager_status` and current policy; intake or a directly selected Manager passes `workflow_id` to `manager_run`, while an already assigned Manager continues its packet directly. To resume locally, use an explicitly saved `network_policy: local-only`; keep the saved execution mode, publication route, valid evidence and open gates. Do not retry historical remote failures while local-only; report them as historical/deferred, never as successful searches or publications. These entry rules also apply when this guide is reached through a skill; common lifecycle instructions do not override the invocation role.

## Full lifecycle

1. **Human prompt / Manager plan.** Apply the entry rule above. Manager coordinates, consolidates and may research, but must delegate bounded specialist work; Manager never performs production implementation or independent self-review. Use exact display names: `SWSD Agent`, `P-RES Agent`, `FnD Agent`, `Reviewer Agent`, `Tester Agent`. Wait for actual delegate results and collect each real invocation ID, `assignment_report` ID and artifact references. Inline role impersonation, manager-authored specialist reports and a proposed handoff do not establish delegation. Missing launch capability, results or reports are blockers with a next action, not permission for Manager to substitute inline work.
2. **Research, SWSD requirements / P-RES architecture.** First load `taskforces-knowledge-reuse`: inspect workspace platform/framework/version evidence and local Cornell notes, search verified local cache with `knowledge_search`, then save applicability, version/feature differences, or a substantive scoped no-match rationale with `knowledge_research`. Under local-only, explicitly say **upstream not searched**; an empty local cache is not a global no-match. Discover commit-pinned upstream sources only when remote access is authorized. Authentication failures (including 401) are failures of that remote operation, never no-match; they do not prohibit policy-authorized local research. Missing/tampered evidence still blocks reuse. Research gates planning and task dispatch. Reuse framework insights, not a whole prior project. Manager delegates to `SWSD Agent` for formal requirements, scope, acceptance and verification criteria (`ready`), and `P-RES Agent` for module architecture, interfaces, supplied Bosch rules and applicable safety standards (`design-ready`). Record at least two distinct specialist contributions with distinct reported invocation IDs. Persist sources, rationale, risks and decisions. Independently review design and check plans before implementation. Ask the human only for unresolved product intent or external blockers.
3. **FnD implementation and build.** Define bounded tasks with `data.workflow_id`, requirement links, acceptance criteria, allowed paths, dependencies, documentation outputs and verification procedures. `FnD Agent` uses supplied Bosch COMAND WF when available, implements production logic and builds before review. Apply software or embedded allocations where required. COMAND WF is an external project tool, not bundled here.
4. **Reviewer sign-off.** Invoke `Reviewer Agent` separately from FnD. Review code against requirements, P-RES architecture, static analysis and supplied standards. Record findings or sign-off on the current baseline. Specialists do not delegate recursively. Serialize shared-state edits and terminals; at most three independent workers.
5. **Tester verification.** `Tester Agent` generates requirement-linked tests with ComVeriX and executes SIL with ECU-Test when configured. Run real checks, archive evidence with immutable input capture, inspect exit status and logs, then summarize reports. Missing required tools block SIL claims; alternate unit/static checks are not SIL. These external tools require project configuration and authorization; no bundled integration is claimed. Complete independent acceptance review of the final evidence baseline; repairs invalidate stale evidence and review.
6. **Cornell findings and consolidation.** Every specialist records seven-section `assignment_report` before returning: Objective, Inputs and Sources, Decisions and Rationale, Results, Evidence, Limitations, Lessons. Task producers also submit their task work record. Record operations use core role IDs from the table below, not display names. Before `manager_finish` and before the substantive user answer, persist a meaningful Cornell note with `note_create({note: {...}})`, including `note.workflow_id` set to this saved workflow ID, same-workflow `requirement_ids` and evidence references, source ledger, cues, main notes, demonstration, practice command/exercise/answer and summary. Cite older external notes as historical context in the source ledger/narrative, not as current evidence or cross-workflow record bindings. Confirm the returned note ID and saved path (`artifact_path`) against the actual saved artifact; a promised note or chat-only summary is insufficient. Observed claims require actual evidence IDs. If saving fails, report a blocker without claiming Cornell delivery or closure. `manager_finish` refuses native closure without a valid evidence-linked Cornell note. Curate qualified generalized lessons with independent review, or record an explicit no-lesson rationale; this does not waive Cornell delivery.
7. **Human release.** Run `manager_finish` only after its engineering gates pass. Under local-only, retain research, Cornell findings and qualified contributions locally and report remote knowledge/archive work as deferred; no upstream request is required for local completion. Later publication requires user opt-in to `network_policy: remote-enabled`, the configured destination and current independent generalization/public-safe review of sanitized content. `automatic_pr: false` keeps manager publication local even when remote-enabled; automatic knowledge publication additionally requires `automatic_pr: true`. Existing policies retain their saved route; `project-branch` uses stable `taskforces/knowledge/<project-hash-prefix>` without PR or merge. See `docs/knowledge-reuse.md` for opt-in and recovery. SQLite is only a rebuildable retrieval index; validated local artifacts and verified Git sources retain their authority. Deliver the full `final_report`, `test_reports` and `cornell_notes` narrative to the human, including the saved Cornell note ID/path, limits and deferred/blocked publication status. Engineering completion is not release approval. Human reviews test reports and Cornell findings and approves release separately. Never merge or publish packages automatically.

## Analysis and research scope

Analysis/research-only requests still require real bounded specialist contributions and a meaningful saved Cornell note before the substantive answer. Manager may inspect sources, research and consolidate, while delegating scoped requirements, architecture, independent review or verification questions to the named specialists as applicable. Preserve sources, findings, rationale, limitations and applicable verification in the note; separate sourced conclusions from untested hypotheses. A source-inspection exercise can demonstrate research findings without pretending code or SIL ran.

Do not invent production changes, builds, code reviews or SIL runs merely to fit a research request. Full engineering gates remain unchanged for engineering changes. This scope guidance does not change storage or lifecycle validation: if the saved increment cannot close under its existing gates, preserve open state, identify the unsatisfied gates and next action, and deliver only the saved, supportable findings without claiming completion or acceptance.

## Six agents, one model configuration

| Agent display name | Persisted core roles                                    | Model tier |
| ------------------ | ------------------------------------------------------- | ---------- |
| Manager Agent      | manager, researcher, codebase-analyst, curator, release | strong     |
| SWSD Agent         | requirements                                            | strong     |
| P-RES Agent        | architect, component-owner                              | strong     |
| FnD Agent          | developer                                               | worker     |
| Reviewer Agent     | reviewer                                                | strong     |
| Tester Agent       | verifier, check-executor                                | worker     |

Edit `.taskforces/routing.json` (`.verythinker/routing.json` before migration): `strong_model`, `worker_models`, and provider/catalog settings when applicable. Run `npx taskforces update` to regenerate all six agent model fields. Ordered worker models are client fallback preferences, not observed execution. User-edited generated files are preserved with review candidates; inspect update conflicts before relying on new selections. Historical core roles and signed Bridge routing remain compatible. Lightweight also uses `Manager Agent` but follows its separate guide.

Every created engineering record and Cornell note must carry the saved workflow ID. Native reported invocation IDs have no signed receipt: inspect `manager_status`, not `native_status`. CLI fallback: `taskforces assignment report --data JSON --body FILE`. An unbound Cornell mutation must reference only records from one native workflow; strict or mixed-workflow references require the proper bound session and cannot be bypassed.

## Assurance boundary

Native IDs, configured models and chat-visible runs are reported observations, not signed runtime receipts. Native workflows and archive manifests carry `unsigned-native-report`, including when engineering acceptance passes. This is not ASPICE certification or provider-issued model attestation. Never invent model access, review, evidence, reasoning effort or signed receipts.

`strict` retains the optional VS Code Model Bridge, invocation-bound sessions and signed routing gates. Saved workflow modes cannot change. Create a new increment when a different assurance mode is required. `lightweight` remains a separate opt-in mode and does not substitute for this full lifecycle.

## Storage migration

Stop all writers and native invocations before `taskforces migrate`. Migration renames the managed directory only: it does not rewrite record bytes, evidence hashes, legacy protocol identities or signed paths. Conflicting roots, locks, linked roots and indeterminate native work block migration. Inspect conflicts rather than merging or overwriting them. Remote repositories are not renamed.
