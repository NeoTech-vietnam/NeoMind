# NeoMind: full Copilot-native lifecycle

Use `copilot-native` for visible VS Code subagents with full engineering gates. Read project automation, routing and archive policies before intake. New native policies use `network_policy: local-only` and `automatic_pr: false`; existing saved policies are preserved, and absent `network_policy` retains legacy remote behavior. Under `local-only`, make zero remote discovery, publication or archive requests; explicit remote tools reject. Required workspace research and Cornell findings stay inside the project. Remote work is deferred, not an engineering waiver. New installations use `.neomind`; unmigrated projects retain `.verythinker`. Serialized historical paths and receipt identities remain unchanged.

## Entry role: decide before intake

When the native client omits invocation identity, follow `reported-assignments.md`: Coordinator prepares each actual delegate packet; the actual delegate claims its server-issued local identity and uses `reported_assignment` for scoped research, discussion and seven-section reports. Read invocation-ID requirements below as an actual available client ID or this explicitly unsigned local identity. Coordinator never claims or reports for specialists. Missing platform IDs do not waive gates or stop otherwise authorized local work.

The universe shows profile names over stable core roles. Use `agent_activity` for unsigned assignment visibility: Coordinator reports running with assignment_id `coordinator`; before a real delegate launch it reports dispatched under a unique assignment_id and passes that ID, workflow_id and exact profile_id in the delegate packet. Each specialist reports running before work, updates at milestones/at least every two minutes during long work, and returns completed/blocked/failed honestly. Dispatch is only an attempt; actual invocation_id is optional and must never be invented. Reports expire after five minutes. Coordinator reports its own final activity before manager_finish. Activity is advisory and never substitutes for required reports, checks or gates.

- **Generic intake** (neither selected Coordinator nor an assigned specialist): call `manager_run` once with the complete request. Launch exactly `NeoMind Coordinator Agent` through VS Code's standard agent tool with the returned `handoff.prompt` unchanged, and wait for its result. A returned handoff is not execution. If launch fails, report the blocker instead of running coordinator steps inline.
- **Directly selected NeoMind Coordinator Agent:** call `manager_run` once for a new user request, then continue the returned prompt and workflow directly in the current invocation. The returned `handoff.agent: NeoMind Coordinator Agent` names yourself; do not launch it. An already assigned Coordinator with a supplied workflow/prompt continues directly without another intake call or self-delegation.
- **Assigned specialists:** execute only the bounded assignment and core role contract. Requirement text in the packet does not authorize intake. Never call `manager_run`, launch Coordinator or delegate recursively. Return actual results, invocation ID and `assignment_report` ID to Coordinator, not workflow closure.

Resume saved workflow IDs instead of duplicating work. For an existing increment, inspect `manager_status` and current policy; intake or a directly selected Coordinator passes `workflow_id` to `manager_run`, while an already assigned Coordinator continues its packet directly. To resume locally, use an explicitly saved `network_policy: local-only`; keep the saved execution mode, publication route, valid evidence and open gates. Do not retry historical remote failures while local-only; report them as historical/deferred, never as successful searches or publications. These entry rules also apply when this guide is reached through a skill; common lifecycle instructions do not override the invocation role.

## Full lifecycle

1. **Human prompt / Coordinator plan.** Apply the entry rule above. Coordinator owns intake, bounded assignments, consolidation and blockers; production implementation and independent review belong to separate specialist invocations. Choose specialists for the actual question and deliverables: `NeoMind Explorer Agent`, `NeoMind Researcher Agent`, `NeoMind Planner Agent`, `NeoMind Architect Agent`, `NeoMind Implementer Agent`, `NeoMind Debugger Agent`, `NeoMind Verifier Agent` and `NeoMind Reviewer Agent`. Launch only the applicable profiles, with explicit ownership and completion criteria. Wait for actual delegate results and collect each real invocation ID, `assignment_report` ID and artifact references. Inline role impersonation, coordinator-authored specialist reports and a proposed handoff do not establish delegation. Missing launch capability, results or reports are blockers with a next action, not permission for Coordinator to substitute inline work.
2. **Research, requirements and architecture.** First load `neomind-knowledge-reuse`: inspect workspace platform/framework/version evidence and local Cornell notes, search verified local cache with `knowledge_search`, then save applicability, version/feature differences, or a substantive scoped no-match rationale with `knowledge_research`. Under local-only, explicitly say **upstream not searched**; an empty local cache is not a global no-match. Discover commit-pinned upstream sources only when remote access is authorized. Authentication failures (including 401) are failures of that remote operation, never no-match; they do not prohibit policy-authorized local research. Missing/tampered evidence still blocks reuse. Research gates planning and task dispatch. Reuse framework insights, not a whole prior project. Use Explorer for source tracing, Researcher for external facts and reuse assessment, Planner for formal requirements, scope, acceptance and verification criteria (`ready`), and Architect for module boundaries, interfaces and applicable project/safety standards (`design-ready`). Record at least two distinct specialist contributions with distinct reported invocation IDs in full mode. Persist sources, rationale, risks and decisions. Independently review design and check plans before implementation. Selecting applicable specialists never waives the saved workflow's engineering gates. Ask the human only for unresolved product intent or external blockers.
3. **Implementation and diagnosis.** Define bounded tasks with `data.workflow_id`, requirement links, acceptance criteria, allowed paths, dependencies, documentation outputs and verification procedures. Implementer produces the scoped behavior and runs the project's required build/checks before review. For a defect, assign Debugger a concrete reproduction, competing hypotheses, diagnostic evidence and regression objective; any repair stays within the assigned developer scope and receives independent review. Implementer and Debugger use the same persisted `developer` role and model route. Apply software/hardware allocations and embedded constraints only where the requirement and selected profile require them. Select project tools from inspected configuration and the agreed verification plan; a named commercial tool is not a default NeoMind prerequisite.
4. **Independent review.** Invoke Reviewer in an invocation that has not implemented or repaired the assignment. Review against requirements, architecture, applicable static analysis and project standards. Record findings or sign-off on the current baseline. Specialists do not delegate recursively. Serialize shared-state edits and terminals; at most three independent workers.
5. **Verification.** Verifier owns strategy, requirement coverage, expected outcomes and evidence analysis on the strong `verifier` route. In this combined native profile, record verification strategy under `verifier` and prescribed execution under `check-executor`, matching the operation and assignment. Execute the reviewed project procedures, archive evidence with immutable input capture, inspect exit status and logs, then summarize reports. Identify unit, integration, simulation, SIL, bench or HIL evidence by the method actually run. Use project-specific tools only when configured, authorized and required by the agreed procedure. Missing required tools block that check or claim; alternate unit/static checks do not establish SIL or HIL. No bundled commercial-tool integration is claimed. Complete independent acceptance review of the final evidence baseline; repairs invalidate stale evidence and review.
6. **Cornell findings and consolidation.** Every specialist records seven-section `assignment_report` before returning: Objective, Inputs and Sources, Decisions and Rationale, Results, Evidence, Limitations, Lessons. Task producers also submit their task work record. Record operations use core role IDs from the table below, not display names. Before `manager_finish` and before the substantive user answer, persist a meaningful Cornell note with `note_create({note: {...}})`, including `note.workflow_id` set to this saved workflow ID, same-workflow `requirement_ids` and evidence references, source ledger, cues, main notes, demonstration, practice command/exercise/answer and summary. Cite older external notes as historical context in the source ledger/narrative, not as current evidence or cross-workflow record bindings. Confirm the returned note ID and saved path (`artifact_path`) against the actual saved artifact; a promised note or chat-only summary is insufficient. Observed claims require actual evidence IDs. If saving fails, report a blocker without claiming Cornell delivery or closure. `manager_finish` refuses native closure without a valid evidence-linked Cornell note. Curate qualified generalized lessons with independent review, or record an explicit no-lesson rationale; this does not waive Cornell delivery.
7. **Human release.** Run `manager_finish` only after its engineering gates pass. Under local-only, retain research, Cornell findings and qualified contributions locally and report remote knowledge/archive work as deferred; no upstream request is required for local completion. Later publication requires user opt-in to `network_policy: remote-enabled`, the configured destination and current independent generalization/public-safe review of sanitized content. `automatic_pr: false` keeps manager publication local even when remote-enabled; automatic knowledge publication additionally requires `automatic_pr: true`. Existing policies retain their saved route; `project-branch` uses stable `neomind/knowledge/<project-hash-prefix>` without PR or merge. See `docs/knowledge-reuse.md` for opt-in and recovery. SQLite is only a rebuildable retrieval index; validated local artifacts and verified Git sources retain their authority. Deliver the full `final_report`, `test_reports` and `cornell_notes` narrative to the human, including the saved Cornell note ID/path, limits and deferred/blocked publication status. Engineering completion is not release approval. Human reviews test reports and Cornell findings and approves release separately. Never merge or publish packages automatically.

## Analysis and research scope

Analysis/research-only requests still require real bounded specialist contributions and a meaningful saved Cornell note before the substantive answer. Coordinator may inspect sources, research and consolidate, while delegating source exploration, external research, requirements, architecture, independent review or verification questions to the named specialists as applicable. Preserve sources, findings, rationale, limitations and applicable verification in the note; separate sourced conclusions from untested hypotheses. A source-inspection exercise can demonstrate research findings without pretending code or SIL ran.

Do not invent production changes, builds, code reviews or SIL runs merely to fit a research request. Full engineering gates remain unchanged for engineering changes. This scope guidance does not change storage or lifecycle validation: if the saved increment cannot close under its existing gates, preserve open state, identify the unsatisfied gates and next action, and deliver only the saved, supportable findings without claiming completion or acceptance.

## Nine profiles, twelve core roles

| Agent display name | Persisted core roles | Native model role | Default tier |
| --- | --- | --- | --- |
| NeoMind Coordinator Agent | manager, curator, release | manager | strong |
| NeoMind Explorer Agent | codebase-analyst | codebase-analyst | worker |
| NeoMind Researcher Agent | researcher | researcher | worker |
| NeoMind Planner Agent | requirements | requirements | strong |
| NeoMind Architect Agent | architect, component-owner | architect | strong |
| NeoMind Implementer Agent | developer | developer | worker |
| NeoMind Debugger Agent | developer, with a diagnostic assignment | developer | worker |
| NeoMind Verifier Agent | verifier, check-executor | verifier | strong |
| NeoMind Reviewer Agent | reviewer | reviewer | strong |

Coordinator is the only user-invocable profile; the other eight are delegates. Display names organize responsibilities without changing the twelve persisted core IDs, core operations or historical records. The generated Coordinator file is `neomind-coordinator.agent.md`; the skill ID remains `neomind-manager`. Update retires the previous manager agent only when its installed ownership hash still matches; edited files retain the installer's review/conflict treatment.

Edit `.neomind/routing.json` (`.verythinker/routing.json` before migration): `strong_model`, `worker_models`, per-role overrides, and provider/catalog settings when applicable. Run `npx neomind update` to regenerate all nine agent model fields. A native profile uses the single model role above for its whole invocation: Coordinator's curator/release work uses `manager`, Architect's component-owner work uses `architect`, and Verifier's check execution uses the strong `verifier` route. Implementer and Debugger share `developer`; they cannot select separate model policies. The optional strict Bridge continues to route the twelve core roles independently. Configured tiers and ordered worker fallbacks are policy preferences, not observations of execution or reasoning effort. User-edited generated files are preserved with review candidates; inspect update conflicts before relying on new selections. Lightweight also uses Coordinator but follows its separate guide.

Every created engineering record and Cornell note must carry the saved workflow ID. Native reported invocation IDs have no signed receipt: inspect `manager_status`, not `native_status`. CLI fallback: `neomind assignment report --data JSON --body FILE`. An unbound Cornell mutation must reference only records from one native workflow; strict or mixed-workflow references require the proper bound session and cannot be bypassed.

## Assurance boundary

Native IDs, configured models and chat-visible runs are reported observations, not signed runtime receipts. Native workflows and archive manifests carry `unsigned-native-report`, including when engineering acceptance passes. This is not ASPICE certification or provider-issued model attestation. Never invent model access, review, evidence, reasoning effort or signed receipts.

`strict` retains the optional VS Code Model Bridge, invocation-bound sessions and signed routing gates. Saved workflow modes cannot change. Create a new increment when a different assurance mode is required. `lightweight` remains a separate opt-in mode and does not substitute for this full lifecycle.

## Storage migration

Stop all writers and native invocations before `neomind migrate`. Migration renames the managed directory only: it does not rewrite record bytes, evidence hashes, legacy protocol identities or signed paths. Conflicting roots, locks, linked roots and indeterminate native work block migration. Inspect conflicts rather than merging or overwriting them. Remote repositories are not renamed.
