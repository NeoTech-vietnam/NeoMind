# Native supporting software

Use this process for bounded supporting scripts, documentation and application tooling in local Copilot or Codex. A persisted contract selects applicable gates per workflow. Existing strict increments and actual embedded/HDL or safety/security behavior keep their full engineering process.

In local VS Code with NeoMind extension 0.9.4 or later, call `neomindAdvanceWorkflow` with `{workflow_id}`. The host obtains and retains its own backend-issued Coordinator credential, derives the current task and stage, dispatches one exact specialist request and reconciles its actual callback. Repeat only for the next substantive stage; wait for a running or unknown delegate. An existing sealed contract resumes without another planning cycle.

For Coordinator actions use the same tool with `{workflow_id, operation, parameters}`. Supported operations are `workflow_plan`, `record_get`, `record_create`, `record_update`, `cornell_research_compile`, `note_create`, `note_validate`, `procedure_register` and `manager_finish`. Supply the selected MCP operation's advertised semantic arguments in `parameters`; authentication is injected by the host and backend authorization still applies. The host also derives `manager_finish.workflow_id`. Use actual returned references for final Cornell compilation, note creation/validation, real candidate registration and closure. Credentials remain in host memory, and interruption never establishes completion. Specialists still open and report their own assignments; the host never claims a specialist packet.

Codex and older VS Code hosts without this tool use the manual steps below.

1. Resume the actual workflow and open the Coordinator's own assignment as described in [reported-assignments.md](reported-assignments.md). Inspect existing source/tools and the working tree first.
2. Call `workflow_plan` once with `process: software-tools`, rationale, title, objective, measurable acceptance criteria, implementation `allowed_paths`, disjoint `verification_paths`, implementation outputs, documentation paths and checks. Outputs and documentation are inside implementation scope; independent checker files belong only to verification scope. Each check declares its argument array, independent checker path in its baseline, expected exit code and timeout. Baselines cover delivered implementation outputs and the checker within those two scopes. All paths are canonical project-relative paths. The backend creates valid linked requirements, task, check plans and decision; callers supply no record IDs or lifecycle fields. Identical retries reuse the same plan. Its scope is immutable.
3. Call `workflow_next` with the Coordinator handle. Launch only the returned private handoff through the real native agent tool. The Implementer receives implementation paths; Verifier receives independent verification paths; Reviewer receives inspection scope. Existing user work stays untouched.
4. After the actual delegate returns, call `workflow_next` with `observation: {state, observation_id}` from that actual call. The backend derives its current managed assignment; `packet_id` is optional when explicitly correlating a callback. States include completed, completed-without-output, failed, cancelled, running and unknown. Keep the observation ID stable on retries. A terminal callback plus the delegate's typed saved result allows continuation. Running or unknown means wait; an old UI observation does not authorize duplicate workers. Dispatch the returned `handoff.native_call` arguments directly when the native client supports that tool.
5. The backend advances Implementer → independent Verifier → independent Reviewer. Implementer calls `assignment_start` with only its handle, then saves actual findings through `assignment_result`: a completed result uses `submit_task: true`; a blocked or failed result omits it or sets false. Verifier authors its independent checker and calls `assignment_check` with only its handle; Reviewer records `assignment_review` with decision and findings. Each saves its own typed result. These tools derive task/check/actor IDs. Failed checks or findings need real repair and fresh evidence. Missing results permit at most two bounded follow-ups preserving the original lineage and partial work.
6. At `ready_for_cornell`, author one readable final research note using returned actual requirements, task, reports and evidence. The compiler can standardize format, but the author supplies substantive explanation, worked examples, practice and separate answers. Validate its saved output, register actual automation as a candidate where applicable, and call `manager_finish` only after real closure gates pass.

On resume, call `workflow_next` for an existing sealed contract. It reconciles an interrupted planning decision and reuses the original records. Historical planning notes and full engineering drafts remain available as history; current software gates use the bound contract. An explicit local applicability disposition can replace specified administrative approval clauses before implementation starts. Its original text, hash, rationale and effective criteria remain visible. It does not claim those historical approvals passed or waive behavioral acceptance, independent verification, negative controls or final review.

Software assignment context returns the full semantic contract and current stage references. The legacy `task_context.max_chars` budget does not trim software acceptance criteria; historical record bodies are available through their disclosed references.

Opening and saving results emit advisory activity automatically. Optional progress calls communicate concrete milestones; periodic heartbeats and internal notes per worker are unnecessary. Local assignment handles are private unsigned correlation and do not prove process independence. Actual separate native invocations, baseline checks and independent reviews provide the required evidence.
