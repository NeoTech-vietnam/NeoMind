# WorkForce

WorkForce receives ordinary requests from Copilot Local, Codex or Universe. The runtime owns worker sessions, engineering state and tool bindings. Workers use the pinned OpenCode engine and the configured custom endpoint model aliases. Client chat models remain independent of worker routing.

## Give work

Open the project in trusted VS Code, connect WorkForce and use Local WF.PM or the Universe request box. Describe the result in your own words and attach its actual files or folder. Submit once. The receipt identifies the saved request; closing the chat leaves execution running while VS Code stays open. Status shows useful artifacts and current evidence. Engine capability and individual client MCP discovery are separate observations.

The intake tools submit, inspect or control saved requests. They never require assignment claims or worker credentials. Copy an issued question ID when forwarding the user's answer to its pending question. An intentional additional request is different from retrying a lost response. Preserve the returned receipt rather than reconstructing an identity.

## Backend-owned workers

When a session includes a backend role, stage and bound tools, that assignment is authoritative. Client intake instructions apply outside that session. Do not submit the request again, launch client agents, reopen setup, read private runtime files, invent IDs/tokens, claim an assignment or call progress repeatedly. Use only the tools advertised for this assignment. Runtime context provides execution facts and this installed guide without exposing project-private configuration.

WF.PM plans and coordinates. WF.SWSD supplies requirements and verification intent. WF.P-RES supplies applicable architecture and module decisions. WF.FnD implements. WF.Reviewer reviews independently before WF.Tester executes independent verification. The backend applies the saved contract and applicable risk obligations. Historical contracts keep their original commitments.

Use existing project tools and qualified procedures first. A match alone does not authorize execution or prove reuse. Preserve unrelated files and read a file before changing it; the backend checks its recorded hash. Run the producer operations actually declared in the assignment. WF.PM uses `workflow_plan` as its single planning result when that contract is advertised; other roles submit professional content through `assignment_report`. The backend supplies the stage outcome, identity and transition.

WF.FnD hands its current outputs to WF.Reviewer, followed by WF.Tester. Its assignment lists producer operations separately from the independent checks scheduled for WF.Tester. When the assigned outputs and producer operations are ready, hand them over with actual artifact references and limitations. Record a concrete defect in an assigned output in `product_findings`; pending independent test execution is expected at this handoff. WF.Reviewer and WF.Tester supply their own independent verdicts. Final acceptance belongs to the backend after those obligations are satisfied.

Requested Cornell note, practice and answer renderings share a semantic research source. Use the advertised Cornell compiler for its managed renderings. Do not overwrite them with ordinary file tools or manufacture a validation pass. Other requested product files remain ordinary scoped outputs.

## Results and recovery

Delivered drafts, reviewed products and independently verified revisions are distinct. Historical successful checks do not verify subsequent edits. Backend and tool errors are technical incidents, never missing business input. A genuine unanswered product question must identify the missing decision and its effect on a criterion. Answering it continues the same saved request.

The runtime retains operation/checkpoint evidence, prevents unchanged failure loops and uses configured strong models for applicable escalation. It must reconcile uncertain effects before replaying a process or accepting results. Workspace scope guards are not an operating-system sandbox for every subprocess. Never report unexecuted tests or incomplete work as accepted.

## Connection and storage

Routing stores aliases and a pointer to the user's existing model catalog; it does not duplicate catalog credentials. A cached real model tool-call check is bound to the build and configuration. A 9router alias observation does not attest the upstream model. Missing or conflicting client registration remains visible separately.

Engine state uses a protected directory outside the project on the project volume. Startup checks available space and the pinned offline dependencies. Closing VS Code stops owned model/runner processes; subsequent execution reconciles durable checkpoints. Records are grouped under `.workforce/requests`, with legacy IDs and signed evidence retained. Local installation exclusions belong in `.git/info/exclude`; the project's `.gitignore` stays untouched.
